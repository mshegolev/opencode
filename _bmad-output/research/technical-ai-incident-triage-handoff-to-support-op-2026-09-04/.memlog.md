- (claim) ref=[1] status=verified class=delivery-guarantee pub=undated — Jira Cloud webhooks are explicitly at-least-once ('might be delivered more than once'); retries up to 5 times with randomized 5-15 min backoff on timeout/408/409/425/429/5xx. Vendor doc plus independent confirmation in the Atlassian developer community retry-policy announcement.
- (claim) ref=[1] status=unverified class=idempotency-pattern pub=undated — Jira sends X-Atlassian-Webhook-Identifier, stable ACROSS RETRIES, plus X-Atlassian-Webhook-Retry. It is the documented dedupe key for redelivery.
- (claim) ref=[1] status=unverified class=failure-mode pub=undated — Jira degrades to ONE attempt per webhook after 30 min without a successful response, and dynamic webhooks expire 30 days after creation/refresh with NO consumer-side error. Two documented silent-gap modes.
- (claim) ref=[1] status=unverified class=delivery-guarantee pub=undated — No ordering guarantee documented by Atlassian; Primary (~30s) and Secondary (~15 min) flows have different latencies, so a bulk-triggered event can land after a later single event. Design as if unordered.
- (claim) ref=[2] status=unverified class=delivery-guarantee pub=undated — Zendesk explicitly refuses a delivery guarantee ('best effort... we cannot guarantee it') and tells consumers to make handlers idempotent. 12-second request timeout; circuit breaker trips at 70%+ errors or 1000+ errors in a 5-minute window. A slow handler trips it alone.
- (claim) ref=[3] status=unverified class=rate-limit pub=2026-04 — ServiceNow inbound REST rate limiting is rule-driven via sys_rate_limit_rules (per user/role, per node, per hour), 429 when the semaphore queue fills. MECHANISM medium confidence; every NUMBER in the source is folklore, single-sourced, community-contributed, hedged. Cheap local fix: read sys_rate_limit_rules_list.do on the target instance before choosing a poll interval.
- (claim) ref=[4] status=unverified class=guidance pub=undated — Webhook-plus-reconciliation-sweep (poll every 15-60 min, backfill gaps) is recommended by webhook-infrastructure and fintech vendors (Payabli, Hookdeck), NOT by any ITSM vendor doc read in this run. Atlassian actively frames webhooks as removing the need to poll, contradicting its own documented guarantees.
- (claim) ref=[5] status=unverified class=auth-pattern pub=2014 — W3C TAG capability-URL guidance is the standing reference for share-a-secret links: HTTPS, unguessable v4 UUID, revocable, per-recipient. Old, and still trusted because the leak vectors it names are structural to HTTP and browsers, and nothing superseded it.
- (claim) ref=[5] status=unverified class=failure-mode pub=2014 — Capability URLs leak via shorteners, address-bar-to-search, and the Referer header from outbound links ON the protected page itself (mitigation: rel=noreferrer). A triage session containing customer data behind a bare unguessable URL inherits all three.
- (claim) ref=[6] status=unverified class=linking-pattern pub=undated — Grafana external dashboard sharing is the closest mature analogue to 'here is the run, read it' for an account-less reader: read-only, ONLY stored queries execute, security rests on link secrecy ('anyone with the URL can access'). Named operational cost: unmetered query load, answered with caching and rate limiting.
- (claim) ref=[7] status=unverified class=failure-mode pub=2025-09 — Atlassian KB documents that marking a JSM comment internal is NOT sufficient: a comment posted public then edited to internal has already dispatched the customer notification, and bug JSDSERVER-6269 leaks internal-comment at-mentions as Jira core notifications. For a bot the trap is any write path that posts first and re-classifies second: post internal-first, never re-classify.
- (claim) ref=[8] status=unverified class=failure-mode pub=undated — Bot comment noise is recognised and under-solved: bot comments notify like human comments, bot-actor attribution does not exempt them, and remedies are blunt (admin notification-scheme changes; a per-ticket suppress switch that silences only the client side). No engineering writeup found from a team that ran an automation-writes-to-every-ticket integration and described controlling the noise.
- (decision) Dedupe key for the loop must be the INCIDENT NUMBER, not the webhook delivery id: a delivery-id dedupe does nothing against the reconciliation sweep, which re-reads incidents the webhook already delivered.
